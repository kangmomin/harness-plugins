# UI 작업 요청 가이드

작업 유형을 먼저 파악한 후, 유형별 맞춤 질문과 **레이아웃 컨펌**을 통해 실행 가능한 Technical Spec을 생성한다.

## 핵심 철학

- **"What" 보다 "Where & How"**: 어디에 어떻게 배치할지를 명확히 한다.
- **기존 코드 우선**: 반드시 기존 구조를 파악한 후 명세를 작성한다.
- **스타일 충돌 선행 분석**: 리팩터링/UI 변경 시 CSS 변수, 테마 토큰, 글로벌 스타일 간 충돌을 Spec 단계에서 사전 분석한다.
- **결정이 필요한 질문만**: 코드·대화로 확정한 항목은 건너뛰고, 결과를 바꾸는 미결 질문은 한 번에 묶는다.
- **유추 가능하면 질문하지 않는다**: 코드베이스에서 답을 찾을 수 있으면 건너뛴다.
- **레이아웃 먼저**: 화면/컴포넌트 생성·수정(유형 A/B/C/D) 시 ASCII 레이아웃을 그려서 유저 컨펌을 받은 뒤 진행한다.

## Phase 1: 작업 유형 선택

`$ARGUMENTS`에서 유형을 유추할 수 있으면 (판별 기준: 페이지/라우트 → 화면, 컴포넌트명 → 컴포넌트, API/페칭/뮤테이션 → API 연동; 만들어줘/추가 → 생성, 바꿔줘/수정/버그 → 수정) 판단한 유형을 알리고 바로 진행한다.

비어있거나 두 개 이상 유형에 걸치면, 반드시 먼저 `AskUserQuestion`으로 질문한다:

```
어떤 작업을 진행하시나요?

1. 화면 생성 — 새 페이지/라우트 추가
2. 화면 수정 — 기존 페이지의 레이아웃/동작 변경
3. 컴포넌트 생성 — 새 컴포넌트 추가
4. 컴포넌트 수정 — 기존 컴포넌트의 UI/로직 변경
5. API 연동 — 새 API 엔드포인트 연동 (데이터 페칭, 뮤테이션)
6. API 연동 수정 — 기존 API 연동의 변경/버그 수정
```

## Phase 2: 유형별 단계적 질문

> 유형 확정 후 MUST: 같은 폴더의 `references/type-specs.md`를 Read하고, **해당 유형의 질문 시퀀스(Part 1)**를 순서대로 진행한다.

각 단계의 항목을 코드·대화와 대조하고, 아직 결정되지 않아 결과를 바꾸는 사항만 질문한다.

| 유형 | 질문 시퀀스 요약 | 레이아웃 컨펌 |
|------|----------------|--------------|
| A 화면 생성 | 페이지 정보 → 렌더링 전략 → 구성 요소 → 데이터 → SEO → 레이아웃 | 필수 |
| B 화면 수정 | 대상 → 변경 내용 → 스타일 충돌 분석(리팩터링 시) → 영향 범위 → As-Is/To-Be 레이아웃 | 필수 |
| C 컴포넌트 생성 | 용도 → 배치 위치 → Props → UI/UX → 데이터 연동 → 레이아웃 | 필수 |
| D 컴포넌트 수정 | 대상 → 변경 내용 → 영향 범위 → 호환성 → As-Is/To-Be 레이아웃 | 필수 |
| E API 연동 | 대상 API → 스키마 → 사용 위치 → 권한(/admin/ 시) → 상태 관리 → 에러/로딩 → 캐싱 | 없음 |
| F API 연동 수정 | 대상 → 변경 내용 → 영향 범위 → Breaking Changes | 없음 |

### 레이아웃 컨펌 루프 (유형 A/B/C/D 공통, 최대 3회)

현재 요청과 같은 레이아웃이 이미 승인됐다면 그 안과 승인 근거를 재사용하고 Phase 3으로 간다. 레이아웃 변경이 있거나 미확정일 때 아래 루프를 실행한다.

1. 수집한 정보로 ASCII 레이아웃을 그려 제시한다: "이대로 진행할까요? (Y / 수정사항 입력)"
2. **Y** → Phase 3으로 진행.
3. **수정사항 입력** → 레이아웃을 수정해 다시 컨펌 (1회 카운트).

| 종료 조건 | 결과 |
|----------|------|
| 유저 Y | 레이아웃 확정 → Phase 3 |
| 수정 3회 도달, 미확정 | 선택지 제시 (아래) |

3회 도달 시:
> "레이아웃 수정이 3회에 도달했습니다.
> 1. 마지막 안으로 확정하고 진행
> 2. 레이아웃 없이 텍스트 설명으로 확정하고 진행
> 3. 수정 계속 (3회 추가)"

## Phase 3: 코드베이스 탐색

Phase 2의 질문 과정에서 **매 단계마다** 코드베이스를 탐색한다. 질문이 끝난 후 별도로 하지 않는다.

### 탐색 대상

```
CLAUDE.md              → 프로젝트 컨벤션
app/ 또는 pages/       → 라우트/페이지 구조
components/            → 공통 컴포넌트
features/              → 기능별 모듈
hooks/                 → 커스텀 훅
lib/ 또는 utils/       → 유틸리티
api/ 또는 services/    → API 호출
types/                 → 타입 정의
styles/                → 전역 스타일
```

### 탐색 원칙

- `Glob`으로 파일 검색, `Grep`으로 키워드/타입 검색, `Read`로 내용 확인
- 유사 기능의 **참조 구현**을 식별하여 패턴을 파악
- 발견한 내용은 즉시 사용자에게 공유 (질문과 함께)

## Phase 4: Technical Spec 출력

> Phase 4 진입 시 MUST: `references/type-specs.md`의 **해당 유형 Spec 템플릿(Part 2)**을 사용해 Spec을 출력한다.

모든 유형에 공통 실행 원칙의 `### 작업 계약`을 포함한다. 권한·소유권에 따른 UI/API 동작은 허용·거부 조건을 별도 AC/EC로 작성하고, 버그 수정은 환경·재현·기대/실제와 원인 가설의 근거를 함께 적는다.

- 유형 A/B/C/D: Phase 2에서 컨펌받은 ASCII 레이아웃을 Spec의 "레이아웃 (확정)" 섹션에 그대로 포함한다.
- 컨펌 없이 Spec을 출력하지 않는다 (유형 A/B/C/D).

### 엣지 케이스 ID 규칙

엣지 케이스 표의 각 행에 **추적 ID**를 부여한다. 후속 스킬(`/fe-harness:e2e-test`, `start-workflow` Phase 7.7)이 이 ID로 검증 커버리지를 대조하므로, Spec 확정 후 ID를 **재배열하거나 재사용하지 않는다**.

| 항목 | 규칙 |
|------|------|
| 형식 | `EC-01`부터 2자리 순번 (`EC-01`, `EC-02`, …) |
| 부여 단위 | 엣지 케이스 표의 각 행 1개 |
| 케이스 삭제 시 | 번호를 당기지 않고 해당 행만 제거 (빈 번호 허용) |
| 참조 구현 열 | 같은 상황을 처리하는 **기존 코드**를 `file:line`으로 기재. 없으면 `-` |

**참조 구현 열이 이 규칙의 핵심이다.** Spec의 기대 동작이 프로젝트 기존 패턴과 어긋나 있어도(예: 다른 화면은 빈 목록에 EmptyState를 띄우는데 이번 Spec만 스켈레톤 유지), 자연어 문장만으로는 유저가 알아채기 어렵다. Phase 3 탐색에서 찾은 참조 구현을 이 열에 남겨두면 Phase 7.7 read-back이 그 이탈을 검출할 수 있다. 참조를 찾지 못했으면 추측해서 채우지 말고 `-`로 둔다.

### 정상 흐름 ID 규칙 (`AC-nn`)

엣지 케이스가 "예외 상황"을 다룬다면, **정상 흐름(Acceptance Criteria)** 은 "성공했을 때 화면이 무엇을 보장하는가"를 다룬다.
`start-workflow`의 TDD 단계(Phase 5.1)가 **테스트 근거의 상한**으로 `EC-nn`과 `AC-nn`만 사용하므로, 정상 흐름에도 ID를 부여한다.

| 항목 | 규칙 |
|------|------|
| 형식 | `AC-01`부터 2자리 순번 |
| 부여 단위 | **관측 가능한 렌더 결과** 1개 (화면/컴포넌트당 보통 1~2개) |
| 조건 | 사용자가 보거나 조작할 수 있어야 한다 — 렌더된 요소·role·텍스트·핸들러 호출 등 |
| 삭제 시 | `EC` 와 동일 — 번호를 당기지 않는다 |

"정상적으로 보인다" 같은 검증 불가능한 문장은 `AC`가 아니다. `목록이 있으면 각 항목이 listitem role로 렌더된다`처럼 **단언 가능한 형태**로 적는다.

Spec을 유저가 직접 제공했거나 구버전이라 표·ID가 없으면 **없는 요구사항을 지어내지 않는다.** 본문에 관측 가능한 조항이 있으면 그 조항에만 ID를 부여하고 `추적 기준: 본문 조항 기반`을, 조항이 하나도 없으면 `추적 기준 없음`을 명시한다.

## 레이아웃 그리기 규칙 (유형 A/B/C/D 공통)

1. **박스 문자 사용**: `┌ ┐ └ ┘ ─ │ ├ ┤ ┬ ┴ ┼` 로 구조를 명확히 표현한다.
2. **각 영역에 이름 표기**: `[Header]`, `상품 이미지`, `[버튼명]` 등 역할을 명시한다.
3. **계층 구조 표현**: 중첩된 영역은 들여쓰기와 내부 박스로 표현한다.
4. **상태별 표현**: 로딩/에러/빈 상태가 중요한 경우 별도로 그린다.
5. **반응형**: 모바일/데스크탑 차이가 크면 둘 다 그린다.
6. **수정 유형**: As-Is와 To-Be를 나란히 그려 변경점을 명확히 한다.
7. **인터랙션 표기**: `▶`, `◀`, `▼`, `×`, `☐`, `☑` 등으로 인터랙션 요소를 표현한다.

## 중요 원칙

1. **미결 질문은 묶는다** — 이미 정해진 대상·완료 조건·승인을 다시 묻지 않는다.
2. **탐색과 질문을 동시에** — 코드를 먼저 보고, 답에 의존하지 않는 작업은 계속한다.
3. **유추 가능하면 건너뛴다** — 코드·대화의 근거를 알리고 진행한다.
4. **유추한 내용은 `[Assumption]` 표기** — 사용자에게 확인을 구한다.
   기존 승인·Assumption Gate에서 확인하고 태그만으로 Spec 작성을 멈추지 않는다.
5. **불필요한 섹션은 생략** — 해당하는 것만 출력한다.
6. **레이아웃 합의는 필수** — 유형 A/B/C/D는 확정 ASCII 레이아웃을 Spec에 남긴다. 같은 안의 기존 승인은 재사용하고 새 안만 컨펌한다.

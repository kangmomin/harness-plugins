# 작업 계약과 실행 원칙

요청 정리·실행·위임 전에 같은 컨텍스트에서 한 번 읽는다. 이 문서만으로 workflow를 시작하거나 해당 스킬의 수정 권한을 넓히지 않는다. be-harness가 정본이며 FE/common은 독립 설치를 위한 동일 사본이다.

## 작업 계약

요청과 기존 대화에서 아래 내용을 짧게 정리해 Spec에 포함한다. 사용자가 이미 제공한 값은 재질문하지 않고, 미지정 항목을 채우기 위한 별도 설문을 만들지 않는다. 결과를 바꾸는 미결 결정만 묻고 그 결정에 의존하지 않는 작업은 계속한다.

```markdown
### 작업 계약
- 대상: 저장소·작업 디렉터리·브랜치, 이슈/문서, 정확한 경로·API·필드 식별자
- 기준: 현재 요구사항·설계 문서와 우선순위, 참조 구현 및 이번 동작에 적합한 이유
- 범위: 바꿀 동작과 제외할 동작
- 완료: 기능 결과·필수 검증 증거, 문서·버전·커밋·push·PR 처리 범위
- 승인: 이미 허용된 대상·변경·외부 효과와 사용자 지시 근거
- 미결: 결과를 바꾸는 결정 또는 없음
```

현재 명시적 요구와 사용자가 지정한 최신 설계 기준을 먼저 대조한다. 과거 작업 기록·기각된 제안은 배경이고, 기존 코드·테스트는 현재 동작의 증거다. 이들이 다르면 차이를 드러내고 업무 의미를 임의로 선택하지 않는다. 선례는 서비스 이름의 유사성보다 실제 동작·데이터·권한 조건의 적합성으로 고른다. 유추한 요구는 추론 태그로 남긴다.
완료 항목은 사용자 요청과 해당 스킬의 모드·출력 계약으로 정한다. 문서·버전·원격 작업을 관성적으로 추가하지 않으며, 현재 설계 문서에는 최종 계약을, 변경 이유·기각 이력은 작업 기록에 남긴다.

## 계획 공유와 승인

- 시스템·호스트 권한 안에서 사용자 지시는 스킬·override의 일반 가이드라인보다 우선한다. 같은 Spec·Plan·대상·효과의 승인은 재사용하고 계획 공유를 새 승인 요청으로 취급하지 않는다. 모드·원격 정책·Assumption Gate·호스트의 필수 승인은 계속 적용한다.
- 기존 승인과 다른 중대한 동작·범위·외부 효과만 추가로 결정받는다. 이미 허용된 준비·검증을 마쳐 구체적인 변경과 필요한 결정을 제시한다. 리뷰어의 APPROVE나 응답 대기를 사용자 승인으로 간주하지 않는다.
- 코드·대화로 확정 가능한 선택은 근거를 알리고 진행한다. 새 추론 사항은 태그로 기록하고 기존 Gate에서 확인하며, 태그만으로 매번 작업을 멈추지 않는다. 파일 규칙 때문에 중단하면 실제 파일 경로·문구와 적용 이유를 밝힌다.
- 서브에이전트 완료 후 다음 허용 단계를 이어간다. 후속 정정·짧은 선택·상태 질문은 현재 목표에 반영하고, 상태 답변 후 작업을 계속한다. 명시적 취소·양립 불가능한 새 요청일 때만 목표를 교체한다.

## 인계와 재개

새 세션·에이전트·브랜치로 넘어갈 때 작업 계약, 최신 결정, 미완료 항목과 승인 근거를 다시 고정한다. 일반 위임 프롬프트에는 이 문서의 절대 경로(먼저 읽기), 정확한 저장소/작업 디렉터리·브랜치·식별자, 배정 범위·완료 증거와 미결 결정을 전달한다. 상태 생성 전에는 필요한 계약 내용을, 생성 후에는 상태의 Spec과 필요한 섹션 경로를 준다. 반환된 결과를 상위 오케스트레이터가 현재 작업에 합친다.
격리 Read-back에는 기존 소스 전용 입력만 준다. 작업 계약·Spec·기준 문서·상태·노트·이 정책을 추가로 전달하지 않는다. 새 worktree에 기존 RUN을 강제로 재사용하지 않으며 경로·재개 검증은 run-lifecycle 계약을 따른다. 상태를 새 템플릿으로 덮어쓰지 않는다.

## 검증과 종료

- 검사 범위, 결함 인정 기준(어느 요구와 어떻게 다른지), 완료에 필요한 증거를 먼저 고정한다. 변경·티어별 필수 검증을 끝낸 뒤 추가 반복은 새 결함 근거, 미검증 가설, 수정 영향이 있을 때만 수행하고 이유를 남긴다. 이미 기각한 제안을 새 근거 없이 되살리지 않는다.
- 필수 Phase·티어 승격·수정 후 재검증·기존 루프 상한과 무진전 종료 규칙을 유지한다. 상한 도달·중단·미검증을 통과로 바꾸지 않는다. 완료한 검증, 미검증 영역, 미해결 결함을 구분해 보고한다.
- 기대값은 요구·기준 문서에서 확정하고 구현 오류, 테스트 오류, 환경 문제를 구분한다. 통과시키려는 기대값 완화·테스트 삭제는 금지한다. 테스트 충돌은 기존 `[TestConflict]`·테스트 수정 권한 계약으로 처리한다. 낮은 영향의 변경에 구현을 그대로 옮긴 테스트를 추가하지 않는다.
- 권한·소유권에 영향이 있으면 일반 사용자 성공, 미인증, 권한 없음, 다른 소유자 자원을 별도 AC/EC로 정리한다. 적용하지 않는 조건은 이유를 적는다. 관리자 계정의 성공은 다른 역할의 증거가 아니며, 토큰·자원이 부족한 케이스는 미검증으로 남긴다.

## 진단 근거

장애 입력은 환경·버전 / 재현 동작·입력 / 기대·실제 / 관련 로그로 요약한다. 사용자 가설은 확정 원인이 아니므로 지지·반박 근거와 가능한 다른 원인을 비교한다. 성능을 이유로 구조를 바꾸기 전에 실제 쿼리·측정 결과를 확인한다. 읽기 전용 역할의 명령 권한을 넓히지 않고 부족한 측정은 호출자에게 요청한다.
Spec·위임 입력·보고서에 로그를 옮길 때 인증 헤더·쿠키·토큰·연결 문자열의 비밀값 등 불필요한 민감값을 마스킹한다. 진단에 필요한 오류 코드·발생 순서·요청 형태는 보존하며, 원본 로그를 수정하거나 비밀값을 장기 상태에 복제하지 않는다.

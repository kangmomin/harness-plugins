# Spec 템플릿과 준비도 기준

## 준비도 기준

| # | 항목 | 충족 조건 |
|---|------|----------|
| 1 | 작업 유형 | 생성/수정/디버깅 중 하나로 확정 (FE는 화면·컴포넌트·API 연동 구분까지) |
| 2 | 대상 특정 | 엔드포인트·화면·컴포넌트·함수 등 정확한 식별자, 수정·디버깅이면 현재 코드 위치 `file:line` |
| 3 | 핵심 요구 | 비즈니스 규칙·입출력이 "조건 → 동작"으로 구체적 |
| 4 | 작업 계약 | 대상·기준·범위·완료·승인·미결 6항목 기재 (값이 없으면 "없음") |
| 5 | 정상 흐름 | `AC` 1개 이상, 모두 외부에서 단언 가능한 결과 |
| 6 | 엣지 케이스 | R4에서 확정한 예외가 `EC`로 기록됨, 기대 동작 빈칸 없음 |
| 7 | 권한·소유권 | 영향이 있으면 일반 사용자 성공·미인증·권한 없음·다른 소유자의 `AC`/`EC`, 없으면 이유 |
| 8 | 디버깅 | `RC` 1개 이상, 입력·현재·기대 열이 모두 채워짐 |
| 9 | FE UI | 화면·컴포넌트 생성/수정이면 확정 레이아웃 또는 텍스트 확정 기록 |
| 10 | 풀스택 | Feature Matrix의 모든 `F` 행에 FE/BE 책임과 완료 조건 |
| 11 | 모순 없음 | 결과를 바꾸는 미결·요구 간 충돌 0건 |

1~4·11은 항상 적용한다. 5~10은 해당하는 유형·도메인에만 적용하고 나머지는 `해당 없음`으로 둔다.

## 추적 ID 규칙

| ID | 대상 | 규칙 |
|----|------|------|
| `AC-nn` | 정상 흐름의 관측 가능한 결과 1개 | "201을 반환하고 body에 id 포함"처럼 단언 가능해야 한다. "정상 동작한다"는 AC가 아니다 |
| `EC-nn` | 엣지 케이스 1개 | 참조 구현 열에 같은 상황을 처리하는 기존 코드 `file:line`, 없으면 `-` (추측으로 채우지 않음) |
| `RC-nn` | 디버깅 재현 케이스 1개 | 기대(수정 후) 열 필수 |
| `F-nn` | 풀스택 사용자 흐름 1개 | Feature Matrix 행 |

공통: `01`부터 2자리 순번, 확정 후 재배열·재사용하지 않고 삭제 시 번호를 당기지 않는다. 수정 유형은 이번 변경으로 **새로 생기거나 달라지는** 동작만 적는다.

## 템플릿

아래 공통 머리말 뒤에 도메인 섹션을 붙인다. 해당 없는 섹션은 생략한다.

```markdown
# Spec: {기능명}

- 상태: {구현 준비 완료 | 초안}
- 유형·도메인: {생성|수정|디버깅} · {backend|frontend|fullstack}
- 작성: {YYYY-MM-DD}, ready-for-impl 인터뷰 (질문 {n}회)

### 작업 계약
- 대상: {저장소·작업 디렉터리·브랜치, 이슈/문서, 정확한 경로·API·필드 식별자}
- 기준: {요구사항·설계 문서와 우선순위, 참조 구현과 선택 이유}
- 범위: {바꿀 동작} / 제외: {제외할 동작}
- 완료: {기능 결과·필수 검증 증거, 문서·버전·커밋·push·PR 처리 범위}
- 승인: {이 Spec 내용 확정까지만. 구현·원격 작업은 승인되지 않음}
- 미결: {미결 ID 목록 또는 없음}

## 기능 목표
{한 문장. "~하면 ~해야 한다"}

## 현재 상황 (As-Is)
| 파일 | 역할 | 수정 필요 |
|------|------|----------|

### 참조 구현
- `path:line` → {따를 패턴과 이유}

## 변경 사항 (To-Be)
{생성: 새 파일·수정 파일 / 수정: 변경 후 동작과 영향 범위}

## 정상 흐름
| ID | 시나리오 | 보장되는 결과 |
|----|---------|--------------|
| AC-01 | | |

## 엣지 케이스
| ID | 케이스 | 기대 동작 | 참조 구현 |
|----|--------|----------|----------|
| EC-01 | | | |

## 결정 로그
| ID | 항목 | 결정 | 근거 |
|----|------|------|------|
| D-01 | | | 사용자 답(R2) / `file:line` |

## Assumption
- [Assumption] {추론 내용} — 근거: {...}

## 미결
- {D-nn}: {무엇을 정해야 하는지, 선택지와 영향}
```

### BE 섹션 (backend·fullstack)

```markdown
## API
| Method | Path | 설명 | 인증 |
|--------|------|------|------|

### Request
| 필드 | 타입 | 필수 | 검증 |
|------|------|------|------|

### Response
| 필드 | 타입 | nullable | 설명 |
|------|------|----------|------|

## 비즈니스 규칙
- {조건} → {동작}

## DB 변경
- [ ] {테이블/컬럼/인덱스/마이그레이션, 없으면 "없음"}

## Breaking Changes
- {있으면 기술, 없으면 "없음"}
```

정상 흐름·엣지 케이스 표에는 `HTTP` 열(또는 gRPC status)을 추가한다.

### FE 섹션 (frontend·fullstack)

```markdown
## 화면/컴포넌트
- 위치: {라우트 또는 부모 컴포넌트}
- 구성: {구성 요소 목록}
- Props: {컴포넌트 생성 시}

## 레이아웃 (확정)
{ASCII 레이아웃 — 수정 유형은 As-Is / To-Be}

## 데이터 연동
| API | 사용 필드 | 호출 시점 | 캐시 무효화 |
|-----|----------|----------|------------|

## UI 상태
| 상태 | 표현 |
|------|------|
| loading / empty / success / error | |
```

```markdown
|----|------------|------------|------------|----------|
| F-01 | | | | |

## 통신 계약 (초안)
- 인터페이스·에러 코드별 화면 처리 요약. Integration Contract와 `CT-nn` 확정은 start-workflow 풀스택 Phase 2에서 한다.
```

```markdown

{문제 설명, 환경·버전}

| ID | 입력·전제 | 현재 (버그) | 기대 (수정 후) | 참조 구현 |
|----|----------|------------|---------------|----------|
| RC-01 | | | | |

## 코드 흐름
{진입점 `file:line` → ... → `file:line`}
```

# 인터뷰 라운드 체크리스트

각 라운드는 아래 항목을 결정 원장과 대조해 **미결인 것만** 묻는다. 항목은 질문 문장이 아니라 확정해야 할 대상이다. 질문을 만들 때는 탐색 결과로 선택지를 구성하고(예: "기존 `order_handler.go:42`처럼 409 반환 (권장)"), 열린 질문은 선택지를 만들 수 없을 때만 쓴다.

표의 `공통` 행은 모든 도메인에, `BE`/`FE` 행은 해당 도메인에 적용한다. 풀스택은 `공통` + `BE` + `FE` + `FS` 행을 모두 적용한다. 디버깅 유형은 R1·R2 대신 §디버깅 라운드를 쓰고 R3부터 해당 항목만 적용한다.

## R1 목표·범위

| 대상 | 확정할 것 |
|------|----------|
| 공통 | 누가(사용자·역할) 무엇을 하려고 하는가, 성공 시 얻는 결과 한 문장 |
| 공통 | 이번 범위에 포함/제외할 동작 (제외를 명시적으로 받는다) |
| 공통 | 기준 문서(이슈·기획·설계 문서)와 우선순위, 서로 다를 때 무엇을 따를지 |
| 수정 | 바뀌기 전/후 동작 차이 한 문장 |
| FS | 사용자 흐름 단위(Feature Matrix 행)와 각 흐름의 FE/BE 책임 분담 |

## R2 동작·인터페이스

| 대상 | 확정할 것 |
|------|----------|
| BE | 엔드포인트(Method·Path 또는 gRPC 메서드·이벤트명), 인증 방식 |
| BE | Request 필드(타입·필수·검증 규칙), Response 필드(타입·nullable), 정렬·페이지네이션 |
| BE | 비즈니스 규칙: 조건 → 동작 (예: "재고 0이면 주문 불가") |
| FE | 화면/컴포넌트 위치(라우트·부모), 구성 요소, 사용자 상호작용 |
| FE | 호출할 API와 사용할 필드, loading/empty/success/error 상태 표현 |
| FE | 컴포넌트 생성이면 Props와 재사용 범위 |
| FS | 화면 행동 ↔ API/이벤트 대응, 응답 필드가 화면 요구를 모두 만족하는지 |

### 레이아웃

FE 화면·컴포넌트 생성/수정이면 R2 질문 후 ASCII 레이아웃을 그려 "1. 이대로 확정 / 2. 수정사항 입력"을 묻는다. 수정이면 As-Is와 To-Be를 나란히 그린다. 수정 입력은 1회로 세고 `{MAX_LAYOUT}`회 상한을 따른다. 확정된 레이아웃은 Spec `레이아웃 (확정)` 섹션에 그대로 넣는다.

## R3 데이터·상태

| 대상 | 확정할 것 |
|------|----------|
| BE | 사용할 테이블·컬럼, 신규 테이블/컬럼/인덱스 여부 (마이그레이션 폴더 근거 제시) |
| BE | 참조 데이터 정합성: 존재하지 않는 ID, 삭제(soft delete)된 레코드, 상태 불일치 시 동작 |
| BE | 트랜잭션 경계, 동시 요청·중복 요청 처리 |
| 공통 | 상태 필드가 있으면 상태 값 목록과 허용 전이 |
| 공통 | 날짜 범위로 상태를 판정하면 저장형/파생형, 경계 포함 여부, 타임존 (기존 패턴을 먼저 찾아 제시) |
| FE | 클라이언트 상태(로컬·서버 캐시·URL) 위치, 캐시 무효화 시점 |

## R4 예외·권한

| 대상 | 확정할 것 |
|------|----------|
| 공통 | 입력 오류·대상 없음·충돌·외부 실패 각각의 기대 동작과 에러 코드 (기존 코드의 같은 상황 처리를 근거로 제시) |
| 공통 | 권한·소유권 영향이 있으면: 일반 사용자 성공, 미인증, 권한 없음, 다른 소유자 자원 — 각각의 기대 동작. 해당 없으면 이유 |
| FE | 에러 메시지 노출 여부, 재시도·폴백 UI, 버튼 비활성 조건 |
| FS | 에러 코드별 화면 처리 |

## R5 비기능·호환·배포

| 대상 | 확정할 것 |
|------|----------|
| 공통 | 기존 클라이언트·호출자와의 호환성 (Breaking change 허용 여부) |
| 공통 | 성능 요구(데이터 규모, 응답 시간)가 결과를 바꾸는 경우만 |
| 공통 | 배포 조건: 마이그레이션 순서, 기능 플래그, 백필이 필요한 경우만 |
| FE | 접근성·반응형·SEO 요구가 있는 경우만 |

## R6 완료·검증

| 대상 | 확정할 것 |
|------|----------|
| 공통 | 정상 흐름 결과를 외부에서 관측 가능한 형태로 (응답 status·필드, 저장 상태, 화면 표시) |
| 공통 | 필수 검증 증거(단위·E2E·수동 확인)와 문서·버전·커밋·PR 처리 범위 |

## 디버깅 라운드

디버깅 유형은 R1·R2 대신 아래를 묻고, 이후 R3~R6 중 수정에 영향을 주는 항목만 적용한다.

| 대상 | 확정할 것 |
|------|----------|
| 증상 | 무엇이 잘못되는가 (에러·누락·잘못된 값·타임아웃) |
| 재현 | 환경·버전, 입력·전제, 재현 빈도 |
| 기대·실제 | 수정 후 기대 동작 — 비워 두지 않는다. 정할 수 없으면 그 이유를 미결로 |
| 근거 | 에러 메시지·로그(비밀값 마스킹), 사용자 가설과 지지·반박 근거 |

## 보충 라운드

Step 4 준비도 점검에서 미충족이 나오면 해당 항목만 모아 묻는다. 본 라운드와 같은 `{MAX_ROUNDS}` 상한을 공유한다.

> 존재하면 추가 규칙/예외로 흡수하고 충돌 시 오버라이드가 우선한다. 상세 규약: 플러그인 루트 `OVERRIDES.md`.

실행 전에 [작업 계약과 실행 원칙](../start-workflow/references/execution-policy.md)을 읽는다.

# Ready for Impl — 구현 전 요구사항 인터뷰

`start-workflow`에 줄 지시를 받은 것처럼 기능 설명을 받되, **구현하지 않고** 인터뷰로 "무엇을 어떻게 만들지"를 확정한다. 결과는 작업 계약과 추적 ID(`AC`/`EC`/`RC`, 풀스택은 `F`)를 갖춘 Spec 파일 1개이며, 이후 `start-workflow` Phase 1의 "이미 상세 Spec이 제공된 경우" 분기를 충족하는 것을 목표로 한다.

- `{MAX_ROUNDS}` = 8 (본 라운드 6 + 보충 2, 레이아웃 컨펌 제외)
- `{MAX_REVISIONS}` = 2 (Step 6 수정 반영 횟수)
- `{MAX_LAYOUT}` = 3 (FE 레이아웃 컨펌 수정 횟수)
- `{SPEC_NAME}` = `YYYYMMDD-<kebab-case-기능명>-spec.md`
- `{INTERVIEW_STOPPED}` = false (사용자가 인터뷰 종료를 지시하면 true, 이후 보충 질문 금지)

## Flags

| 플래그 | 효과 |
|--------|------|
| `--be` / `--fe` / `--fs` | 도메인을 확정하고 Step 1의 도메인 판정을 생략한다 (하나만 허용, 둘 이상이면 "대상 플래그는 하나만 지정하세요" 후 종료) |
| `--out <경로>` | 저장 위치. `.md`로 끝나면 파일, 아니면 디렉터리(파일명은 `{SPEC_NAME}`). 상대 경로는 현재 작업 디렉터리 기준 |

## 금지 사항 (모든 Step 공통)

- 소스·설정·마이그레이션·테스트 파일을 만들거나 수정하지 않는다. `Write`는 Step 7의 Spec 파일 1개에만 쓴다.
- 브랜치 생성·커밋·push·PR, 서버 기동, DB 쓰기를 하지 않는다. `Bash`는 `git log`/`git diff`/`git status` 같은 읽기 명령에만 쓴다.
- `start-workflow`나 구현 스킬을 자동 호출하지 않는다. Spec 확인은 구현·push·PR 승인이 아니다.
- 추천안·무응답·시간 경과를 사용자 결정으로 취급하지 않는다.

## 질문 방식 (모든 Step 공통)

- `AskUserQuestion`으로 묻고, 호출당 질문 1~4개, 질문당 선택지 2~4개, 권장안을 첫 선택지에 두고 라벨 끝에 `(권장)`을 붙인다. 각 선택지 설명에 근거(`file:line` 또는 대화 출처)를 한 줄 적는다.
- `AskUserQuestion`이 없으면 같은 내용을 번호 매긴 선택지로 출력하고 응답을 기다린다. 응답을 받을 수 없는 실행(서브에이전트·비대화형)이면 남은 질문을 미결로 기록하고 `BLOCKED:NON_INTERACTIVE`로 종료 경로에 들어간다: Step 5로 `초안` Spec을 작성하고, `--out`·`specDir`가 질문 없이 쓸 수 있는 경로일 때만 저장하며, 그 밖의 경우(경로 없음·충돌·work-log 위임 포함) 질문하지 않고 Spec 전문과 미결을 대화에 출력한 뒤 끝낸다. 이후 Step으로 다시 들어가지 않는다.
- 코드·문서·대화로 확정되는 항목은 묻지 않고 근거와 함께 결정 원장에 `확정`으로 적는다. 사용자가 이미 답한 내용을 다시 묻지 않는다.

### 결정 원장

인터뷰 내내 아래 표를 유지하고, 라운드가 끝날 때마다 변경된 행만 짧게 보여 준다.

| ID | 항목 | 상태 | 값 | 근거 |
|----|------|------|----|------|
| D-01 | | 확정 / 추론 / 미결 | | 사용자 답(R2) / `file:line` / 설계 문서 |

- `추론`은 Spec에서 `[Assumption]`으로 표기한다. 결과를 바꾸는 추론은 다음 라운드에서 확인한다.
- 나중 답변이 이전 결정을 바꾸면 해당 행을 갱신하고, 그 결정에 의존하는 행을 `미결`로 되돌려 다시 점검한다.
- 요구·설계 문서·현재 코드가 서로 다르면 임의로 고르지 않고 `미결`로 올린다.

## Step 1: 요청·유형·도메인 판정

`$ARGUMENTS`와 대화에서 기능 설명과 플래그를 분리한다. 설명이 비어 있으면 "어떤 기능을 구현하려고 하나요?"를 묻는다.

| 축 | 값 | 판별 단서 |
|----|----|----------|
| 작업 유형 | 생성 / 수정 / 디버깅 | 만들어줘·추가 → 생성, 바꿔줘·변경 → 수정, 에러·버그·안 됨 → 디버깅 |
| 도메인 | backend / frontend / fullstack | 플래그 > 요청 단서(API·DB·배치 → BE, 화면·컴포넌트·폼 → FE, "API 만들고 화면도" → FS) > 프로젝트 신호(`go.mod`·`package.json` 의존성·`.claude/*-harness.local.md`) |

근거가 일치하면 `판정: {유형} · {도메인} — {근거}` 한 줄을 알리고 진행한다. 충돌하거나 판단 불가일 때만 두 축을 한 번의 질문으로 묻는다. 검토(리뷰) 요청이면 이 스킬 대상이 아니므로 `SKIPPED:NOT_IMPLEMENTATION`과 함께 리뷰 스킬을 안내하고 종료한다.

## Step 2: 선행 탐색

질문 전에 답을 찾을 수 있는 것을 먼저 찾는다. 탐색 범위가 넓으면 `Explore` 에이전트에 결론만 요청한다.

1. 프로젝트 지침: `CLAUDE.md`, `.claude/*-harness.local.md`의 `projectConventions`·`sourceDirs`.
2. 참조 구현: 같은 도메인·유사 동작의 기존 코드(Handler/Usecase/Repository, 페이지/컴포넌트/훅, 스키마·마이그레이션)와 `file:line`.
3. 수정·디버깅이면 대상 코드의 현재 동작을 요약한다.
4. 설계 문서·이전 기록: 세션 스킬 목록에 설계 문서 검색 스킬이나 `work-log:search`가 있으면 그 스킬로 관련 문서를 찾는다. 없으면 생략한다(`SKIPPED:NO_DOC_SOURCE`, 보고에만 표기).

결과로 결정 원장 초안을 만들고, 사용자에게 "현재 상황" 요약(5줄 이내)과 확정·미결 개수를 보여 준다.

## Step 3: 인터뷰 라운드

> Step 3 진입 시 MUST: 같은 폴더의 `references/interview-rounds.md`를 Read하고, 판정한 유형·도메인에 해당하는 라운드 체크리스트를 사용한다.

본 라운드 순서: **R1 목표·범위 → R2 동작·인터페이스 → R3 데이터·상태 → R4 예외·권한 → R5 비기능·호환·배포 → R6 완료·검증**.

라운드마다:

1. 체크리스트 항목을 결정 원장과 대조해 `미결`만 고른다. 미결이 없으면 그 라운드는 질문 없이 넘어간다(라운드 수에 세지 않음).
2. 직전 답변으로 새 API·테이블·화면·외부 연동이 드러났으면 그 범위만 추가 탐색해 근거를 갱신한다.
3. 결과를 가장 크게 바꾸는 질문부터 최대 4개를 묶어 묻는다. 4개를 넘으면 다음 라운드로 넘긴다.
4. 답을 결정 원장에 반영하고 변경 행을 보여 준다.

FE 화면·컴포넌트 생성/수정이면 R2 안에서 ASCII 레이아웃 컨펌 루프를 수행한다(상세: `references/interview-rounds.md` §레이아웃). 같은 레이아웃이 이미 승인됐으면 재사용한다.

### 종료 조건

| 조건 | 결과 |
|------|------|
| 결과를 바꾸는 `미결` 0건 | `DONE` → Step 4 |
| 사용자가 "여기까지" 등 인터뷰 종료를 지시 | `{INTERVIEW_STOPPED}` = true, 남은 미결을 Spec `미결` 섹션에 기록 → Step 4 |
| 사용자가 취소 | `SKIPPED:USER_CANCELLED` — 저장 없이 종료 |
| 질문 호출 `{MAX_ROUNDS}`회 도달, 미결 잔존 | `BLOCKED:MAX_ROUNDS` → 아래 선택지 |
| 레이아웃 수정 `{MAX_LAYOUT}`회 도달 | FE request와 같이 "1. 현재 안으로 확정 / 2. 텍스트 설명으로 확정 / 3. 중단" 선택 |

`BLOCKED:MAX_ROUNDS` 선택지:

```
인터뷰 질문이 {MAX_ROUNDS}회에 도달했지만 미결 {N}건이 남았습니다: {미결 ID 목록}
1. 미결을 그대로 두고 초안 Spec 저장 → Step 5 (상태: 초안)
2. 남은 미결을 권장안으로 일괄 확정 → 해당 행을 [Assumption]으로 기록하고 Step 4
3. 중단 → 저장 없이 종료
```

## Step 4: 준비도 점검

> Step 4 진입 시 MUST: 같은 폴더의 `references/spec-template.md`를 Read하고 §준비도 기준으로 점검한다.

준비도 기준의 모든 항목을 `충족 / 미충족 / 해당 없음(사유)`으로 판정한다. 미충족이 보충 질문으로 해결 가능하고 `{INTERVIEW_STOPPED}`가 false이면 Step 3의 보충 라운드로 돌아간다(`{MAX_ROUNDS}` 상한 공유 — 횟수를 초기화하지 않는다). `{INTERVIEW_STOPPED}`가 true이거나 해결 불가하거나 상한에 도달하면 다시 묻지 않고 해당 항목을 미결로 두고 Spec 상태를 `초안`으로 정한다.

| 결과 | Spec 상태 |
|------|----------|
| 전 항목 충족 또는 해당 없음 | `구현 준비 완료` |
| 미충족·미결 1건 이상 | `초안` (start-workflow 인계 시 해당 미결부터 다시 확인 필요) |

## Step 5: Spec 작성

`references/spec-template.md`의 도메인별 템플릿으로 Spec을 작성한다.

- 결정 원장의 `확정`은 본문에, `추론`은 `[Assumption]` 태그와 근거를 붙여 본문에, `미결`은 `## 미결` 섹션에 둔다.
- 추적 ID(`AC`/`EC`/`RC`/`F`) 규칙은 템플릿을 따른다. 없는 요구를 지어내 ID를 채우지 않는다.
- 해당 없는 섹션은 생략한다.

## Step 6: 사용자 확인

Spec 요약(목표 1줄, 범위·제외, AC/EC 개수, 미결, Assumption 목록)과 전문을 보여 주고 묻는다:

```
이 Spec으로 저장할까요?
1. 저장 → Step 7
2. 수정사항 입력 → 반영 후 Step 4 재점검 → 다시 확인
3. 중단 → 저장 없이 종료
```

수정 반영은 `{MAX_REVISIONS}`회까지다. 수정으로 결정이 바뀌면 결정 원장 전파 규칙을 적용한다. 상한 도달 시 `BLOCKED:MAX_REVISIONS`로 "1. 현재 내용으로 저장(남은 요청은 미결 섹션에 기록) / 2. 중단"을 묻는다. 1을 고르면 남은 요청을 결정 원장에 `미결`로 넣어 의존 행을 전파하고, 질문 없이 Step 4 판정만 다시 수행해 상태를 갱신한 뒤(미결이 있으면 `초안`) Step 7로 간다.

## Step 7: 저장과 인계

저장 위치는 먼저 해당하는 하나만 사용한다.

1. `--out` 경로
2. 오버라이드의 `specDir`
3. 세션에 `work-log:edit` 스킬이 있으면 그 스킬에 Spec 원문과 문서 유형 `spec`을 전달해 저장을 위임한다. 그 스킬의 root 확인·중복 확인·질문 계약을 따르며, 이 스킬이 work-log 설정·init·서버 재시작을 직접 하지 않는다. 위임이 실패하거나 저장 여부가 불명확하면 4로 간다.
4. 질문: "1. 저장 경로 입력 / 2. 대화에 출력만"

직접 쓰는 경우(1·2·4-1):

- 대상 파일이 이미 있으면 덮어쓰지 않는다. 디렉터리 지정이면 `-2`, `-3` 접미사로 새 이름을 쓰고, 파일 지정이면 "1. 다른 경로 입력 / 2. 대화에 출력만"을 묻는다.
- 디렉터리가 없으면 만들지 않고 같은 선택지를 묻는다.
- 쓴 뒤 `Read`로 다시 읽어 저장을 확인한다. 실패하면 경로·원인을 보고하고 Spec 전문을 대화에 출력한다(`FAIL`).

## 출력 형식

```markdown
## Ready for Impl: {기능명}

- 상태: {구현 준비 완료 | 초안}
- 판정: {유형} · {도메인}
- 저장: {절대 경로 | work-log: {경로} | 대화 출력만}
- 인터뷰: 질문 {n}회 · 결정 {확정 a / 추론 b / 미결 c}
- 추적 ID: AC {n} · EC {n} · RC {n} · F {n}

### 미결 / Assumption
- {ID}: {내용} — {상태}

### 다음 단계
- 같은 세션: `/common:start-workflow {도메인 플래그} "위 Spec으로 구현"`
- 새 세션: `/common:start-workflow {도메인 플래그} "{Spec 절대 경로}의 Spec을 Read해 구현"`
- 초안이면: 미결 {ID 목록}을 먼저 정한 뒤 이 스킬을 다시 실행하거나 start-workflow Phase 1에서 확정
```

## 상태 코드

| 코드 | 의미 |
|------|------|
| `DONE` | Spec 저장(또는 사용자가 고른 대화 출력) 완료 |
| `SKIPPED:NOT_IMPLEMENTATION` | 검토 요청 등 구현 대상이 아님 |
| `SKIPPED:USER_CANCELLED` | 사용자가 중단 |
| `SKIPPED:NO_DOC_SOURCE` | 설계 문서·이전 기록 검색 수단 없음 (진행은 계속) |
| `BLOCKED:MAX_ROUNDS` | 인터뷰 상한 도달, 미결 잔존 |
| `BLOCKED:MAX_REVISIONS` | Spec 수정 상한 도달 |
| `BLOCKED:NON_INTERACTIVE` | 사용자 응답을 받을 수 없음 — 초안만 작성 |
| `FAIL` | Spec 파일 저장 실패 |

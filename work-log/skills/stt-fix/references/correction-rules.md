# STT 보정 규칙 · 규칙 JSON 작성법

> 이 문서는 `stt-fix` 스킬의 Step 4(치환 규칙 작성)와 Step 6(질문 설계)에서 로드된다. 단독 실행 금지.
> 플레이스홀더(`{HELPER}`, `{SCRATCH}` 등)는 SKILL.md 상단 정의를 그대로 쓴다.

## 1. 표기 3단

| 표기 | 언제 | 예 |
|------|------|----|
| 무표기 치환 | 단어장 ✅·(문맥) 확정 패턴, 또는 선행·후행 발화가 직접 뒷받침하는 명백한 오인식 | `커버네티스` → `쿠버네티스` |
| `(?)` | 문맥상 유력하지만 단정할 수 없는 보정. 보정 결과 바로 뒤에 붙인다 | `상품이` → `상준님(?)이` |
| `[불명확: 원문]` | 해독 불가 구간. 내용을 지어내지 않고 원문을 괄호 안에 그대로 둔다 | `[불명확: 성준이 너무]` |

`(?)`는 어절 안에 붙인다(`상준님(?)이`). 어절 뒤에 띄어 쓰면 마커 추출이 그 어절을 잡지 못한다.
`[불명확: …]` 안에 `(?)`를 넣지 않는다. 한 어절에 `(?)`를 두 개 넣으면 헬퍼가 `(?)` 단위로 나눠 각각 별도 마커로 묻는다(`상준님(?)` / `과상우님(?)이`) — 한 어절에는 하나만 두는 것이 질문이 깔끔하다.

## 2. 보존 규칙

- 타임스탬프·화자 라벨·발언 순서·턴 수는 원본 그대로. 헬퍼가 헤더 줄을 치환 대상에서 빼고 턴 수·헤더 일치를 검증한다.
- 말더듬·필러·구어체·반복은 원본대로 둔다. **의미가 바뀌는 오인식만** 고친다.
- 숫자·날짜·금액은 원문 유지. 문맥이 확실할 때만 `(?)`를 붙여 보정한다.
- 영어 약어는 대문자 표준화만 한다(`에이피아이`→`API`). 서비스 코드(FPS·OPS·OCS·AGS·MIM·PMS·NMS 등)는 **서로 치환하지 않는다** — 음가가 비슷해도 다른 서비스다.
- 요약·의역·문장 재배열 금지. 보정본은 전사이지 회의록 요약이 아니다.

## 3. 단어장 규칙 수집 우선순위

단어장(`{DICT}`)과 공유 사전을 Read로 전부 읽은 뒤 규칙을 모은다.

1. **✅ 사용자 확인** > **(문맥) 확정** > **(?) 추정**. 같은 원문에 등급이 다른 항목이 있으면 높은 등급만 쓴다.
2. **뒤 섹션이 앞 섹션을 대체한다.** 증분 섹션(`## YYMMDD … 보정에서 추가된 패턴 — <ID>`)은 시간순으로 뒤에 붙으므로, 같은 원문은 가장 뒤의 결정을 따른다.
3. **반례 기록이 지목한 이전 규칙은 수집에서 제외한다.** 예: "1차 보정 `송하림` 폐기 → `송화림`"이 있으면 `송하림`으로 가는 규칙은 만들지 않는다.
4. 공유 사전(`--shared-dict`)에서는 **인명·서비스 코드·도구명**만 가져온다. 일반 어휘 추정은 가져오지 않는다. 본 프로젝트 사전과 충돌하면 본 프로젝트 사전이 우선한다.
5. 사전의 (?) 추정 항목은 이번 전사에서도 (?)를 유지한다. 사전에 (?)로 적혀 있다고 무표기 치환하지 않는다.

## 4. 위험도 분류

| 등급 | 범주 | 처리 |
|------|------|------|
| **고위험** | 인명·호칭 / 서비스·제품·도구·채널명 / 일정·금액·수치 / 결정 사항을 바꾸는 동사(한다↔안 한다) | 단어장 ✅ 패턴이 아니면 반드시 `(?)`. Step 6 질문의 기본 범위 |
| 저위험 | 일반 어휘·조사·어미·띄어쓰기 | 문맥 근거가 있으면 무표기, 약하면 `(?)`. 기본 질문 범위 밖(사용자가 '전체'를 고르면 포함) |

## 5. 인명 판별 규칙

- **교차 확인 2개 이상**이 있을 때만 무표기 치환한다: ① 호명 직후 본인 응답(1인칭) ② 역할 서술과 직전 회의록 참석자·역할 일치 ③ 단어장 §2 확정 용어 ④ 같은 전사 안의 다른 표기(실명 호명 등). 하나뿐이면 `(?)`.
- **음가 다수결 금지.** STT 변형이 여러 개일 때 가장 많이 나온 음가를 정답으로 삼지 않는다(반례: `하림` 4회였지만 실제는 `송화림`). 변형이 2개 이상인 인명은 단어장 ✅가 없으면 반드시 `(?)` + 사용자 확인.
- **유사 인명 쌍**은 역할·문맥으로만 가른다. 단어장 §3 판별 규칙에 적힌 쌍(예: 상준님=인프라·인력 배치 / 상우님=기획·강의)을 먼저 적용하고, 규칙이 없으면 `(?)`.
- 단어장·직전 회의록·전사 어디에도 없는 인명은 보정하지 않고 원문 + `(?)`를 붙인다(예: `정아님(?)`). 새 인명은 Step 8 증분 섹션의 '신규 인명·용어'에 올린다.
- 호칭 접미(님·씨·선생님·소장님)는 원문을 따른다. `이름이`→`이름님이`처럼 조사가 붙은 오인식은 호칭을 복원한다.

## 6. 보정 금지·유지

- 서비스 코드 상호 치환 금지(§2).
- 화자가 의도적으로 쓴 외래어·은어·사내 약칭은 유지한다. 단어장 §3 '보정 금지·유지' 목록을 먼저 확인한다.
- 숫자·단위·날짜는 원문 유지.
- 원문이 이미 올바른 표기이면 단어장 패턴이 있어도 바꾸지 않는다(헬퍼는 ASCII 영숫자 old에만 단어 경계를 자동 적용하므로, 한글 old는 부분 일치에 주의 — 예: `강희`→`강인`은 `강희님`뿐 아니라 `강희진`도 바꾼다. 어절 단위로 old를 잡는다).

## 7. 규칙 JSON 작성법 (`{SCRATCH}/rules.json`)

```json
{
  "global": [["상주님", "상준님"], ["커버네티스", "쿠버네티스"], ["GK", "GKE"]],
  "turns": {
    "0": [["상품이", "상준님(?)이"]],
    "17": [["래퍼", "레포"], ["성준이 너무", "[불명확: 성준이 너무]"]]
  }
}
```

| 항목 | 규칙 |
|------|------|
| `global` | 전사 전체에 적용. 전사에서 한 번도 매치되지 않으면 `unused_rules`에 경고로만 남는다(실패 아님) |
| `turns` | 키 = **턴 서수(0부터)** — `initial.json.changes[].turn`·`markers[].turn`과 같은 값. 타임스탬프가 아니다(중복 시각이 흔하다). 그 턴에서 **정확히 1회** 매치해야 하며 아니면 `scoped_mismatch`로 실패 |
| old | 비어 있을 수 없다. 리터럴로 매치된다(정규식 아님). 같은 위치에 여러 old가 겹치면 긴 old가 이긴다 |
| 단어 경계 | old가 ASCII 영숫자만이면 양쪽 경계를 자동 적용한다(`GK`는 `GKE`를 건드리지 않음). 한글·혼합 old는 경계 없음 |
| 같은 old 충돌 | `global`과 `turns[n]`에 같은 old가 있으면 그 턴에서는 scoped가 이긴다 |
| 단일 패스 | 한 턴의 모든 규칙은 원문에 대해 한 번에 적용된다. 어떤 규칙의 출력도 다른 규칙의 입력이 되지 않는다. `상주님`→`상준님`과 `상준님`→`…`을 함께 넣어도 연쇄되지 않는다 |
| 마커 | `(?)`·`[불명확: …]`는 **new 안에 직접** 넣는다. 헬퍼가 마커를 만들어 주지 않는다 |
| 헤더 줄 | 치환되지 않는다. 화자 라벨을 바꾸려면 보정본 '참석자 (추정)' 표에만 적는다 |
| 줄바꿈 | new에 줄바꿈을 넣지 않는다. 빈 줄 뒤에 타임스탬프 모양이 생기면 `structure_changed`로 실패 |

### 실패 코드 처리

| `failures[].kind` | 원인 | 조치 |
|---|---|---|
| `scoped_mismatch` (`hits` 0) | 그 턴에 old가 없음 — 턴 서수 착오 또는 원문 표기 차이(띄어쓰기·NFC) | `initial.json`/원문에서 턴 서수와 정확한 원문을 다시 확인 |
| `scoped_mismatch` (`hits` ≥ 2) | 같은 턴에 old가 여러 번 | old를 앞뒤 어절까지 넓혀 유일하게 만든다 |
| `structure_changed` | new가 헤더 모양·줄바꿈을 만들었거나 old가 줄바꿈을 포함 | 해당 규칙의 new를 한 줄로, 헤더 모양 금지 |
| `bad_rules` | JSON 형식·키 범위·빈 old | 메시지의 `reason`대로 수정 |
| `turns_mismatch` | `--expect-turns`와 결과 턴 수 불일치 | 원본 턴 수(`probe.json.turns`)를 다시 확인 |
| `exists` | `--write-md`/`--write-txt` 대상이 이미 있음 | 그 파일만 다른 이름으로 다시 생성하거나 생략. 함께 `created`된 파일은 재생성하지 않는다 |
| `outside_root` / `same_as_source` | vault 밖 쓰기, 경로에 심볼릭 링크·`..` 포함, 또는 원본 덮어쓰기 시도 | 경로를 `{ROOT}` 안의 실제 디렉터리 아래 새 파일로 바꾼다 |
| `unknown_marker` / `phrase_mismatch` / `duplicate_decision` / `invalid_action` | 결정 JSON이 `initial.json.markers`와 맞지 않음 | `marker_id`를 `initial.json`에서 다시 복사. `approve`는 `(?)`에만, `restore`는 `[불명확]`에만 |
| `overlapping_markers` | 한 턴에서 결정 대상 구간이 겹침 — 결정 JSON의 `marker_id`가 다른 본문(예: 수정 전 `body1.txt`가 아닌 파일)에서 나왔을 때 | `--src`가 `initial.json`을 만든 본문과 같은지 확인하고 ID를 다시 복사 |

## 8. 질문 설계 (Step 6)

- 한 질문 = 한 `marker_id`가 기본. 같은 문장에 마커가 둘이고 답이 함께 정해지면 한 질문으로 묶되, 질문 본문에 대상 `marker_id`를 모두 적고 결정 JSON에는 ID별로 한 건씩 쓴다.
- 질문에는 **시각·화자·원문·1차 보정·근거**를 적는다. 근거가 없으면 "근거 없음(음가 유사)"라고 적어 사용자가 보류를 고를 수 있게 한다.
- Other(자유 입력)로 받은 수정 문구는 표시한 `phrase` 전체를 대체한다. 조사까지 포함해 받는다(`상준님(?)이` → "상준님이").
- `[불명확: …]` 항목은 '원문 복원'이 승인에 해당한다. 사용자가 다른 문구를 주면 `fix`.
- 보류는 마커를 그대로 둔다. 보류 항목은 Step 8 증분 섹션의 '추정 잔존'/'판독 불가'에 그대로 올린다.

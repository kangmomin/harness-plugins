# 오버레이 규약 (Overlay Convention)

특화 하네스(`minmos-harness`, `hyeondongs-harness`)가 베이스 하네스(`be-harness`, `fe-harness`)의 절차를 **복제하지 않고 그 위에 델타만 얹는** 방식을 정의한다.

스킬을 새로 만들거나 특화 하네스를 추가할 때 이 문서를 기준으로 작성한다. 작성 표준 일반은 `docs/skill-authoring.md`가 canonical이며, 이 문서는 그중 **오버레이에만** 적용되는 규약이다.

## 1. 원칙

| # | 원칙 |
|---|------|
| 1 | **절차는 베이스에만 존재한다.** 오버레이는 절차를 복제하지 않고 "무엇을 더하고/바꾸고/치환하는지"만 기술한다. |
| 2 | **오버레이는 베이스의 Phase 번호에 의존하지 않는다.** 위치는 절대 번호가 아니라 **앵커**로 지정한다 (§4). |
| 3 | **범용 기능은 베이스로 승격한다.** 오버레이가 베이스보다 나은 범용 절차를 갖게 되면 그것은 오버레이가 아니라 베이스의 결함이다 (§6). |
| 4 | 오버레이가 베이스 동작을 **역행**시키는 것은 가능하지만, 사유를 문서에 기록한다. |

## 2. 두 적용 경로

| 경로 | 위치 | 적용 시점 | 적용 범위 |
|------|------|----------|----------|
| **A. 플러그인 내장** | `{plugin}/overlay/{skill}.md` | 위임 스킬(`/{plugin}:{skill}`) 호출 시 Read | 그 호출 1회 |
| **B. 프로젝트 복사** | `.claude/{base-plugin}/skills/{skill}.md` | `/{plugin}:init` 이 A를 복사 | 이후 `/{base-plugin}:{skill}` 직접 호출 전부 |

경로 B는 기존 **Project Overrides** 레이어(`{base-plugin}/OVERRIDES.md`)를 그대로 사용한다. 따라서 베이스 스킬은 오버레이를 위해 수정할 필요가 없다 — 이미 `.claude/{plugin}/skills/{name}.md`를 Read하는 머리말을 갖고 있다.

### 2.1 중복 적용 방지 (CRITICAL)

두 경로가 동시에 존재하면 같은 규칙이 두 번 적용되어 Phase가 중복 삽입될 수 있다. **위임 스킬이 경로 B를 먼저 확인한다:**

```
1. `.claude/{base-plugin}/skills/{skill}.md` 를 Read 시도
2. 존재하고 `<!-- overlay-source: {plugin}@{version} -->` 마커가 있으면
   → 경로 B가 이미 설치됨. 경로 A(`{plugin}/overlay/{skill}.md`) 로드를 **생략**하고 베이스에 위임
3. 없으면 → 경로 A를 Read하여 베이스에 전달
```

경로 B로 복사된 파일은 첫 줄에 반드시 출처 마커를 포함한다:

```markdown
<!-- overlay-source: minmos-harness@2.0.0 -->
```

마커가 없는 `.claude/{base-plugin}/skills/{skill}.md`는 **사용자가 직접 작성한 프로젝트 오버라이드**이므로 경로 A와 함께 적용한다 (중복이 아니다).

## 3. 오버레이 문서 표준 섹션

```markdown
<!-- overlay-source: {plugin}@{version} -->

## Base
{base-plugin}:{skill}

## Pre-flight 추가
| 점검 항목 | 확인 방법 | 누락 시 영향 |

## Phase 삽입
| 앵커 | 위치 | 삽입 단계 | 절차 |

## Phase 치환
| 앵커 | 대체 절차 |

## 스킬 치환 매핑
| 베이스가 호출하는 것 | 치환 대상 |

## 추가 규칙
[베이스 전 구간에 적용되는 규칙]

## References
| 파일 | 로드 시점 |
```

해당 없는 섹션은 생략한다. 순서는 바꾸지 않는다.

## 4. 앵커 기반 위치 지정 (CRITICAL)

오버레이가 `Phase 4.5`, `Phase 10` 같은 **절대 번호**를 쓰면 베이스가 Phase를 추가·삭제하는 순간 위치가 어긋난다. 오버레이는 항상 **앵커**로 지정한다.

### 4.1 앵커 표기

앵커는 `Phase {번호} ({제목})` 형식으로, **베이스 SKILL.md에 실제로 존재하는 제목**을 그대로 인용한다. 실행 시에는 번호가 아니라 **제목으로 매칭**한다 — 번호가 달라져도 제목이 같으면 같은 앵커다.

| 위치 지시어 | 의미 |
|------------|------|
| `앞` | 앵커 Phase 시작 **전**에 실행 |
| `직후` | 앵커 Phase 완료 **직후**에 실행 |
| `치환` | 앵커 Phase를 **대체** (베이스 절차 미실행) |
| `내부: {하위 단계}` | 앵커 Phase의 특정 하위 단계에 삽입 |

### 4.2 삽입 단계의 번호 표기

삽입된 단계는 베이스 번호와 충돌하지 않도록 `Phase {앵커번호}+` 로 표기한다. 앵커 하나에 삽입이 둘 이상이면 `Phase {앵커번호}+1`, `+2` 로 순서를 매긴다.

```
베이스: Phase 8 (품질 루프) → Phase 9 (API 문서 동기화)
오버레이: Phase 8 직후에 "Codex 품질 리뷰" 삽입
실행 시: Phase 8 → Phase 8+ (Codex 품질 리뷰) → Phase 9
```

상태 파일의 `Phase Assignments` 표에도 `8+` 형식 그대로 기록한다.

### 4.3 앵커 소실 처리 (graceful degradation)

베이스가 개편되어 앵커 제목을 찾을 수 없으면:

| 감지 | 폴백 | 고지 문구 |
|------|------|----------|
| 앵커 제목이 베이스 SKILL.md에 없음 | 해당 삽입/치환을 `SKIPPED:ANCHOR_NOT_FOUND`로 기록하고 **베이스 절차를 그대로 진행** | "오버레이 앵커 `{앵커}` 를 베이스에서 찾지 못했습니다. 해당 항목(`{삽입 단계명}`)을 건너뜁니다 — `{plugin}` 오버레이 갱신이 필요합니다." |

앵커가 없다고 워크플로우 전체를 중단하지 않는다. 베이스는 오버레이 없이도 완결적으로 동작해야 한다.

## 5. 위임 스킬 작성 규칙

특화 하네스의 위임 스킬은 **절차를 갖지 않는다.** 아래 구조를 따른다 (목표 50줄 이내):

```markdown
---
name: {skill}
description: "{베이스 기능 한 줄}. **{plugin} 오버레이**({델타 요약})를 얹어 실행한다. {트리거 조건}."
allowed-tools: Read, Glob, Skill
user-invocable: true
argument-hint: {베이스와 동일}
---

# {Skill} ({plugin} 오버레이)

`{base-plugin}:{skill}` 에 `{plugin}` 오버레이를 얹어 실행한다. **이 문서에 절차는 없다.**

> 실행 시 MUST: `docs/overlay.md` §2.1의 중복 적용 방지 절차를 따라 오버레이 소스를 결정한 뒤,
> `${CLAUDE_PLUGIN_ROOT}/overlay/{skill}.md` 를 Read하고 그 내용을 "베이스 절차에 적용할 델타"로 보유한 채
> Skill tool로 `/{base-plugin}:{skill}` 를 호출한다.

## 오버레이 요약
[무엇이 더해지는지 3~5줄. 상세는 overlay 문서가 canonical]

## 전제 조건
- `{base-plugin}` 플러그인 선행 설치. 미설치 시: [고지 문구] 후 종료.
```

- 인자는 **해석하지 않고 그대로** 베이스에 전달한다.
- 베이스 출력은 **가공하지 않고 그대로** 상위에 올린다.
- `SKIPPED:*` / `BLOCKED:*` 는 그대로 전파한다.

## 6. 승격 / 오버레이 분류 기준

오버레이에 넣을지 베이스로 올릴지는 아래 기준으로 판정한다.

| 기준 | 귀속 |
|------|------|
| 도메인 무관 + 범용 가치 (루프 제어, 리포트 형식, 회귀 대조 등) | **베이스 승격** |
| 특정 조직·프로젝트의 도구/인프라에 종속 (사내 MCP, 사내 문서 시스템, 사내 시크릿 경로) | 오버레이 |
| 특정 프로토콜·스택 확장 (gRPC/PubSub 테스트 절차 등) | 오버레이 (베이스가 그 스택을 전제하지 않는 한) |
| 조직 고유 코드 컨벤션 | 오버레이 |

**오버레이가 베이스보다 나은 범용 절차를 갖고 있으면 그것은 베이스의 결함이다.** 오버레이로 방치하지 말고 베이스로 승격한 뒤, 오버레이에는 특화분만 남긴다.

## 7. 오버레이가 하지 않는 것

- 베이스 절차를 복제하지 않는다 (`docs/skill-authoring.md` §9 복붙 금지).
- 베이스 플러그인의 **파일 경로를 참조하지 않는다.** 베이스 호출은 Skill tool의 스킬 이름으로만 한다 (§9 cross-plugin 규칙). 오버레이 문서가 참조할 수 있는 파일은 **자기 플러그인 내부**(`${CLAUDE_PLUGIN_ROOT}/overlay/...`)뿐이다.
- 베이스의 Phase 번호를 재부여하지 않는다 (§4).
- 상태 파일 포맷을 바꾸지 않는다. 삽입 단계는 기존 `Phase Assignments` 표에 행을 추가하는 방식으로만 기록한다.

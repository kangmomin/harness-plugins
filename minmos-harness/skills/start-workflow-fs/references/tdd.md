> 이 문서는 `start-workflow-fs` 스킬의 Phase 6(baseline 수집), Phase 7.1(Red), Phase 7.2(Green), Phase 8(도메인 품질 루프)에서 로드된다. 단독 실행 금지.
> `{STATE_FILE}` 등 플레이스홀더 정의는 SKILL.md 본문을 따른다.

# 계약 기반 TDD 통합 규약

풀스택에서 테스트를 먼저 쓰는 이유는 회귀 탐지에 더해 **contract drift 탐지**다.
BE는 계약이 약속한 응답을, FE는 계약이 약속한 소비를 각각 테스트로 고정하면, 한쪽이 계약에서 이탈하는 순간 그 테스트가 깨진다.

단일 도메인과 달리 fs에는 Spec 하나가 없다. **frozen Integration Contract와 Feature Matrix가 테스트 근거다.**

## 추적 ID 체계

| ID | 부여 대상 | 부여 Phase |
|----|----------|-----------|
| `F-nn` | Feature Matrix의 각 사용자 흐름 행 | Phase 1 |
| `CT-nn` | Integration Contract의 각 검증 가능한 조항 (필드·status·에러 코드·상태 전이) | Phase 3 |
| `EC-nn` | 각 도메인 `request` 산출물의 엣지 케이스 (있을 때만 승계) | Phase 1 |

- ID는 계약 확정 후 **재배열하거나 재사용하지 않는다.** Phase 10.1 3방향 대조가 이 ID로 매칭한다.
- 계약이 바뀌면(Phase 3 복귀) 해당 `CT-nn`은 번호를 유지한 채 내용만 갱신하고, 연결된 테스트를 다시 Red로 되돌린다.

## TDD 적용 판정

Phase 6에서 확인하고, 하나라도 걸리면 TDD를 SKIP한다. **도메인별로 따로 판정한다** — BE만 SKIP되고 FE는 활성일 수 있다.

| # | 조건 | 상태 코드 |
|---|------|----------|
| 1 | `$ARGUMENTS`에 `--no-tdd` | `SKIPPED:USER_OPT_OUT` (양 도메인) |
| 2 | 해당 도메인의 테스트 명령이 비어있음 | `SKIPPED:NO_TEST_COMMAND` (해당 도메인만) |
| 3 | 해당 도메인 러너가 스위트를 발견하지 못함 | `SKIPPED:NO_TEST_INFRA` (해당 도메인만) |
| 4 | 계약에 검증 가능한 조항이 0개 | `SKIPPED:NO_TEST_BASIS` (양 도메인) |

# Phase 6: 도메인별 회귀 Baseline 수집

**자율 실행 진입 직전에 수집한다.** 유저와 대화 가능한 마지막 지점이므로 수집 실패 시 선택지를 제시할 수 있다.

BE·FE **각각** 수집해 `{STATE_FILE}`에 도메인별로 기록한다 (템플릿: `references/contract-templates.md`).

| 필드 | 의미 |
|------|------|
| `러너 완주` | 러너가 전체 스위트를 발견·실행 완료했는지. `N`이면 실패 목록을 신뢰할 수 없다 |
| `실패 목록` | `{테스트 식별자} :: {정규화 시그니처}` |
| `정규화 시그니처` | 실패 메시지 첫 줄에서 경로·라인·타임스탬프를 제거한 문자열 |

한쪽 도메인의 수집이 실패해도 **다른 도메인은 계속 진행한다.** 실패한 도메인만 `regression 판정 불가`로 기록한다.

수집 실패 시:
> "{도메인} 테스트 baseline 수집에 실패했습니다: {에러 요약}
> 1. **이대로 진행** — 해당 도메인은 `regression` 판정 불가를 기록하고 `new_red`만 추적
> 2. **중단** — 기존 테스트를 먼저 고치고 재시작
> 3. **해당 도메인만 `--no-tdd`** — 그 도메인은 TDD 없이, 반대쪽은 TDD로 진행"

# Phase 7.1: 계약 테스트 우선 (Red) — 배리어 필수

## 테스트 소유권 (CRITICAL)

계약 테스트를 양쪽이 각자 쓰면 같은 파일을 동시에 건드리거나, 아무도 안 쓰거나 둘 중 하나가 된다. **owner를 먼저 못 박는다.**

| 테스트 종류 | owner | 대상 |
|------------|-------|------|
| BE 로컬 | 백엔드 에이전트 | handler·usecase 단위 테스트 — `CT-nn`의 서버 측 보장 |
| FE 로컬 | 프론트엔드 에이전트 | 컴포넌트·훅 테스트 — `CT-nn`의 클라이언트 측 소비 |
| **공용 계약 스키마** | **오케스트레이터** | 양쪽이 공유하는 DTO·스키마·generated client 검증 |

공용 계약 테스트를 도메인 에이전트가 수정하면 파일 소유권 원칙(SKILL.md `Split By Ownership`) 위반이다.

## 실행 순서

```
① BE·FE 에이전트 병렬 — 각자 담당 테스트 + 스텁만 작성
   금지: 상대 도메인 파일 수정 / 공용 계약 테스트 수정 / git commit
   반환: { CT-nn·F-nn ID, 테스트명, 파일, 진단 분류 } 또는 `N/A(영향 없음)` 증거

② [배리어] 오케스트레이터가 확인:
   - 계약이 영향을 주는 **모든 도메인**이 유효 Red 또는 명시적 N/A를 반환했는가?
   - 한쪽이라도 미반환/불완전이면 Phase 7.2로 넘어가지 않는다.

③ 오케스트레이터가 공용 계약 테스트 작성 + 도메인별 TDD Test Map 기록 + Red 커밋
```

**한쪽만 Red가 된 상태로 Green을 시작하지 않는다.** BE가 먼저 구현을 끝내면 FE 테스트가 검증할 계약이 이미 코드로 굳어져, 계약이 아니라 BE 구현을 따라가게 된다.

`N/A(영향 없음)` 는 근거를 동반해야 한다 — "이번 계약 변경이 이 도메인의 관측 가능한 동작을 바꾸지 않는다"를 파일 단위로 제시한다.

## Red 에이전트 프롬프트

TDD 활성 시에만 실행한다. 두 에이전트를 **같은 메시지 내에서 병렬 호출**하고, 검증·기록·커밋은 오케스트레이터가 배리어에서 단독 수행한다.

```
Agent tool:  (× 2 — 백엔드 / 프론트엔드)
  subagent_type: general-purpose
  model: [계약 조항 수·도메인 복잡도 기준 선택]
  effort: [동일 기준]
  prompt: |
    상태 파일 `{STATE_FILE}`을 읽고, **{Backend|Frontend} 담당 범위**의 계약 기반 테스트를 작성하세요.
    프로젝트 루트: {CWD}
    현재 Phase: Phase 7.1 (Red) — {Backend|Frontend}
    남은 Phase: Phase 7.2, 8, 9, 10, 11, 12
    배정 model/effort: {model}/{effort}

    ## 근거 (이것만 사용)
    frozen Integration Contract의 `CT-nn` / Feature Matrix의 `F-nn`
    / 해당 도메인 Spec의 `EC-nn` (있을 때만)
    근거 밖의 테스트는 작성하지 마세요.

    ## 담당 범위
    - 백엔드: handler·usecase 단위 테스트 — 계약이 약속한 **응답**을 검증
    - 프론트엔드: 컴포넌트·훅 테스트 — 계약이 약속한 **소비**를 검증

    ## 금지 (CRITICAL)
    - 상대 도메인 파일을 수정하지 마세요.
    - **공용 계약 스키마 테스트를 수정하지 마세요.** 오케스트레이터 소유입니다.
    - 실제 구현을 작성하지 마세요. 컴파일을 위한 **빈 스텁**만 허용됩니다.
    - git commit 을 하지 마세요. 커밋은 오케스트레이터가 처리합니다.

    ## 보고
    { 근거 ID, 테스트명, 파일, 진단 분류 } 매핑 표를 반환하세요.
    이번 계약 변경이 담당 도메인의 관측 가능한 동작을 바꾸지 않으면
    `N/A(영향 없음)` 과 그 **근거를 파일 단위로** 제시하세요.
```

**배리어**: 두 에이전트가 모두 유효 Red 또는 근거 있는 `N/A`를 반환해야 Phase 7.2로 진행한다.
그 뒤 오케스트레이터가 공용 계약 테스트를 작성하고, 도메인별 TDD Test Map을 기록하고, 단일 Red 커밋을 만든다.

## 유효 Red

**① 스위트가 컴파일된다 ② 대상 테스트가 실행된다 ③ 실패 원인이 계약이 요구하는 미구현 동작에 귀속된다.**

컴파일 에러·러너 크래시는 Red가 아니다. 테스트 ID당 총 3회 상한으로 스텁을 보강하고, 도달하면 `cannot_compile`로 기록한 뒤 해당 테스트를 되돌린다.

## Red 커밋

```bash
git add [BE·FE 테스트 파일 + 스텁 + 공용 계약 테스트]
git commit -m "Test: {기능 요약} — 계약 기반 실패 테스트 선작성 (Red)"
```

커밋은 BE/FE를 나누지 않고 **하나의 Red 커밋**으로 묶는다. 계약이 단일 산출물이기 때문이다.

## Phase 7.1 종료 판정

| 조건 | 결과 |
|------|------|
| 영향받는 모든 도메인이 유효 Red 또는 N/A | `DONE` → Phase 7.2 |
| 일부 ID가 `cannot_compile` | `DONE` — 해당 ID 제외하고 Phase 7.2 |
| 한 도메인 전체가 `cannot_compile` | `BLOCKED:NO_VALID_RED` — 해당 도메인만 TDD SKIP하고 Phase 7.2 진행 |
| 계약 조항 자체가 모호해 테스트를 쓸 수 없음 | **Phase 3 복귀** (아래 참조) |

# Phase 7.2: 병렬 구현 (Green)

기존 BE/FE 구현 프롬프트(`references/agent-prompts.md`)에 아래를 **추가로** 전달한다.

```
    ## TDD 규칙 (Phase 7.1에서 계약 기반 테스트가 선작성되었습니다)
    - **테스트 파일을 수정하지 마세요.** 테스트를 고쳐서 통과시키는 것은 금지입니다.
    - 공용 계약 테스트는 오케스트레이터 소유입니다. 열어보되 수정하지 마세요.
    - 테스트가 잘못되었다고 판단되면 코드와 테스트 어느 쪽도 고치지 말고
      `[TestConflict]` 태그로 보고하세요.
    - Phase 7.1이 만든 스텁을 실제 구현으로 채우세요.
    - 통과 기준: 담당 도메인의 `## TDD Test Map` 전체 통과
      AND 해당 도메인 `## Test Baseline` 대비 신규 실패 0건
```

## `[TestConflict]` 판정 — 계약 우선

단일 도메인과 달리 fs에는 **`No Silent Contract Drift`가 우선한다.**

| 상황 | 판정 | 행동 |
|------|------|------|
| **계약 조항 관련** (`CT-nn` 연결 테스트) | 계약 문제 | **Phase 3으로 복귀.** 계약을 고치고 `CT-nn`을 갱신한 뒤 해당 테스트를 다시 Red로 되돌린다. 코드는 건드리지 않는다 |
| 도메인 내부 로직 관련 (계약 무관) | 테스트 오류 | 오케스트레이터가 테스트를 수정하고 Test Map 갱신 |
| 판단 불가 | 계약 문제로 간주 | 안전한 쪽으로 — Phase 3 복귀 |

계약 관련 충돌을 오케스트레이터가 임의 판정하면 그것이 곧 silent contract drift다. **애매하면 계약을 다시 연다.**

# Phase 8: 도메인별 회귀 대조

각 도메인 품질 루프에서 테스트 실행 결과를 해당 도메인의 `## Test Baseline`과 대조한다.

| # | 조건 | 분류 |
|---|------|------|
| 1 | 해당 도메인 `## TDD Test Map`에 등재된 테스트의 실패 | `new_red` |
| 2 | baseline에 동일 식별자 + **동일** 시그니처 | `pre_existing` |
| 3 | baseline에 동일 식별자 + **다른** 시그니처 | `regression` |
| 4 | baseline에 없는 식별자의 실패 | `regression` |
| 5 | 3·4 판정 전 **1회 재실행**, 결과가 뒤집히면 | `flaky` |

수정 우선순위: `regression` → `new_red`. `pre_existing`은 범위 밖이므로 보고만 한다.

**공용 계약 테스트의 실패는 도메인 루프가 고치지 않는다.** 어느 쪽 구현이 계약에서 이탈한 것이므로 오케스트레이터가 원인 도메인을 판정해 배정하고, 계약 자체가 문제면 Phase 3으로 복귀한다.

## 테스트 판정 (도메인별)

| 판정 | 조건 |
|------|------|
| `PASS` | `regression` 0건 + `new_red` 0건 |
| `WARN` | `flaky`만 존재 |
| `FAIL` | `regression` 1건+ 또는 `new_red` 1건+ |

**양 도메인이 모두 `PASS`여야** Phase 8 루프를 탈출한다 (SKILL.md 본문 참조).

# Phase 10.1 격리 규칙 보강

기존 격리 3규칙에 **네 번째 조항**을 추가한다:

> ④ 도메인별 `## TDD Test Map`을 계약 복원 에이전트에 **전달하지 않는다.**
> Test Map은 `CT-nn` ↔ 테스트 매핑이므로, 이를 본 에이전트는 계약을 역추론하게 되어 격리가 무너진다.

부수 효과: TDD가 활성이면 양 도메인 모두 테스트 파일이 존재하므로, Phase 10.1의 BE·FE 복원 소스가 **양쪽 다 확보**된다. 계약 테스트가 곧 "이 도메인이 실제로 약속하는 것"의 가장 정확한 기록이다.

# 어휘 규칙

| 필드 | 허용 값 | 등장 위치 |
|------|--------|----------|
| Phase 상태 | `DONE` `IN_PROGRESS` `PENDING` `SKIPPED:{사유}` `BLOCKED:{사유}` `FAIL` | Phase 진행 상태 열 |
| 판정 | `PASS` `WARN` `FAIL` | 도메인별 테스트 판정 |
| **진단 분류 (데이터)** | `red_assertion` `already_satisfied` `cannot_compile` `deferred_e2e` `regression` `pre_existing` `new_red` `flaky` | `## TDD Test Map` 과 회귀 대조 표의 셀 안에서만 |

**진단 분류가 Phase 진행 상태 열에 등장하면 규약 위반이다** (`docs/skill-authoring.md` §5).
